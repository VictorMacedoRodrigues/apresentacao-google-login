07 / COMO O SITE SE APRESENTA AO GOOGLE

O Google precisa saber
qual site está pedindo.

01 / IDENTIFICAÇÃO

Client ID

É o identificador público da aplicação. Pense no número de cadastro do Campus no Google. Ele não é uma senha nem um Client Secret.

02 / ENDEREÇO

Origem autorizada

É o endereço permitido para usar esse cliente. Neste projeto: https://victormacedorodrigues.github.io — sem o nome do repositório.

03 / RESPOSTA

Callback

É a função que recebe o resultado. No fluxo com popup, o Google entrega a credencial ao JavaScript; o site usa essa resposta para continuar.

Exemplo: o Google reconhece “este pedido veio do Campus, no endereço cadastrado” e devolve o resultado ao ponto de recebimento configurado.

08 / OS PADRÕES POR TRÁS DO LOGIN

Identificar alguém e
dar permissão são coisas diferentes.

AUTORIZAÇÃO / OAUTH 2.0

O que o aplicativo pode fazer?

OAuth 2.0 é um padrão para conceder acesso limitado. Exemplo: autorizar um aplicativo a consultar sua agenda, sem entregar a senha da conta.

AUTENTICAÇÃO / OPENID CONNECT

Quem está entrando?

OpenID Connect, ou OIDC, acrescenta identidade ao OAuth 2.0. O ID Token informa qual usuário foi autenticado. Exemplo: reconhecer Marina no portal.

Google Identity Services oferece ferramentas para esses fluxos. No Campus, usamos o login; não pedimos acesso à agenda, ao Gmail ou ao Drive.

10 / O RETORNO DO LOGIN

ID Token:
a credencial de identidade.

PARA O LOGIN

ID Token

Significa token de identificação. É uma mensagem assinada pelo Google com dados da conta e da validade. O site deve verificar essa credencial antes de confiar nela.

PARA ACESSAR UMA API

Access Token

É um token de acesso: permite chamar uma API dentro das permissões concedidas. Por exemplo, consultar a agenda após uma autorização específica.

No Campus

O botão retorna um ID Token. Recebê-lo não concede acesso automático a outros dados da conta.

O ID Token não é a senha Google e não é a sessão do Campus. A sessão da aplicação vem depois da validação no servidor.

11 / O FORMATO E A PROTEÇÃO

JWT e JWS:
nomes parecidos, papéis diferentes.

JWT / JSON WEB TOKEN

Organiza as informações

JWT é um formato compacto para transportar declarações, chamadas claims. JSON (JavaScript Object Notation) organiza dados em campos e valores: por exemplo, um campo de nome com o valor Marina.

JWS / JSON WEB SIGNATURE

Protege com assinatura

JWS define como representar conteúdo protegido. No ID Token do Google, essa proteção usa uma assinatura digital para verificar a origem e detectar alterações.

A relação

O ID Token do Google é um JWT assinado, representado como JWS compacto. JWT descreve as informações; JWS dá a estrutura assinada.

Assinatura não é criptografia do conteúdo: o payload pode ser lido. Por isso, ler os dados não prova que o token é autêntico.

12 / AS TRÊS PARTES DO TOKEN DO GOOGLE

Cabeçalho, conteúdo
e assinatura.

HEADER·PAYLOAD·SIGNATURE
01 / CABEÇALHO

Header

Indica o algoritmo de assinatura e a chave utilizada. Algoritmo é o método de cálculo; a chave pública permite conferir a assinatura do Google.

02 / CONTEÚDO

Payload

Reúne as claims: informações sobre a conta, quem emitiu o token, para qual aplicação ele vale e quando expira.

03 / ASSINATURA

Signature

Permite detectar alterações e verificar a origem. Se alguém troca o nome ou a validade, a assinatura original deixa de corresponder.

Na representação compacta do ID Token do Google, essas três partes são separadas por pontos. Isso é uma estrutura de dados, não uma senha.

13 / COMO LER AS INFORMAÇÕES

Cada campo responde
a uma pergunta.

sub subject

Qual conta? Identificador único e estável da conta Google; o site o usa para reconhecer a mesma pessoa.

iss issuer

Quem emitiu? Identifica o emissor da credencial. Neste login, deve ser o Google.

aud audience

Para qual aplicação? Deve corresponder ao Client ID esperado pelo site.

exp expiration

Até quando vale? Define o momento de expiração; uma credencial vencida deve ser rejeitada.

Nome, e-mail e foto servem para o perfil. O sub serve como identificador da conta: o e-mail pode mudar sem a pessoa virar outro usuário.

16 / A CONFERÊNCIA DE SEGURANÇA

Decodificar é ler.
Validar é conferir.

1

Assinatura: o servidor usa as chaves públicas do Google para verificar origem e integridade.

2

Emissor e audiência: confere iss e aud para aceitar uma credencial do Google destinada a este site.

3

Validade: confere exp para não aceitar um token expirado.

4

Conta local: só depois da validação associa o sub ao usuário e decide o acesso.

Em produção, use uma biblioteca adequada de verificação. No Campus, o navegador lê o perfil e confere alguns campos; não valida a assinatura nem protege conteúdo privado.

17 / O QUE ACONTECE DEPOIS DA VALIDAÇÃO

O token confirma a entrada.
A sessão mantém o acesso.

01 / IDENTIDADE

Reconhecer Marina

Após validar o ID Token, o servidor encontra ou cria a conta local associada ao identificador da conta Google.

02 / SESSÃO

Lembrar da entrada

O site cria sua própria sessão. Ela permite reconhecer Marina nas próximas solicitações, normalmente usando um cookie seguro.

03 / PERMISSÕES

Liberar o que é dela

O servidor verifica o que essa conta pode acessar. Entrar não significa ter permissão para abrir qualquer curso ou pedido.

Exemplo: Marina pode entrar no portal, mas um curso comprado por outra pessoa continua restrito. Ao sair, o site deve encerrar sua própria sessão.
